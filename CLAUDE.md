# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Start dev server (backend + frontend HMR) on http://localhost:3000
npm run build     # Production build (npm test → vite build → dist/; MDX docs compile here)
npm run preview   # Serve production build locally
npm run lint      # TypeScript type-check (tsc --noEmit; does NOT compile MDX)
npm test          # Rule self-test gate (scripts/ruleSelfTest.ts): ReDoS + dedup + false-positive
npm run clean     # Remove dist/
```

`npm run lint` (tsc) and `npm test` (rule gate) are the CI checks. Note that `lint` does **not** compile the in-app MDX docs — only `npm run build` does (via the `prebuild` → `npm test` → `vite build` chain), so MDX syntax errors surface at build time.

## Architecture

**ClaudeSec** is a real-time AI agent observability dashboard. It ingests OpenTelemetry (OTLP) traces from AI agents (e.g., Claude Code), detects security threats, and visualizes agent activity as a live interactive graph.

### Data flow

```
AI agent → POST /v1/traces (OTLP JSON) → server.ts
  → threat detection (regex rules)
  → SQLite (spans.db)
  → Socket.io broadcast
  → App.tsx (dashboard views: timeline, alerts, orchestration, etc.)
```

### Two-process model in one repo

- **`server.ts`** — Express backend. Handles OTLP ingestion, SQLite reads/writes, security rule evaluation, REST endpoints (`/api/graph`, `/api/export`, `/api/reset`), and Socket.io events. Also serves the Vite-built `dist/` in production.
- **`src/App.tsx`** — Main React frontend component. Uses Socket.io client for live updates and holds all UI state (filters, active tab, session selection). Shows a `WelcomeScreen` on first run (zero sessions). Default tab is Timeline.

### Key architectural decisions

- **SQLite via `better-sqlite3`** persists spans across server restarts (`spans.db` is gitignored but created automatically).
- **Dagre** computes graph layout on the server side (via `/api/graph`) for the headless graph API. There is no graph UI tab in the dashboard.
- **Threat detection** lives in `server.ts` as `SEVERITY_RULES` (183 core regex rules) concatenated with `EXTRA_SEVERITY_RULES` from `severityRulesExtra.ts` (447 gated rules) for ~630 total: prompt injection, credential/secret theft, reverse shells & C2, supply-chain, exfiltration, recon, cloud-metadata SSRF, container escape, crypto-mining, privilege escalation. Evaluated against every incoming span. New rules go in `severityRulesExtra.ts` and must pass `scripts/ruleSelfTest.ts` (ReDoS heuristic + ReDoS execution gate + dedup + false-positive gate). `npm test` runs `ruleSelfTest.ts`, and `prebuild` runs `npm test` — so a ReDoS-prone or duplicate rule fails the build.
- **Enforcement** is the same rule set applied at *two* points: (1) **detection** in `server.ts` (post-hoc, against every ingested span) and (2) a **PreToolUse hook** (`.claude/hooks/claudesec-enforce.cjs`) that can block a Claude Code tool call *before it runs*. The hook is **monitor-by-default** (logs "would-block" to `POST /api/enforce-log`, never blocks except an always-on catastrophic-6 floor) and **fails open** on any error/missing config. `enforce` mode actively denies (exit 2). The server is the source of truth: mode + per-rule overrides live in the SQLite `config` table, are exposed via `GET/PUT /api/enforce/config`, and are mirrored to `enforce-config.json` (path overridable via `CLAUDESEC_ENFORCE_CONFIG`) which the hook reads each call. The block-rule snapshot the hook compiles is `rules-enforcement.json`, regenerated by `scripts/build-enforcement-rules.cjs`. Honest scope: this is the agent-specific, bypassable (`CLAUDESEC_HOOKS_BYPASS=1`) Claude Code hook layer — not an OS sandbox; cross-agent/MCP enforcement is future work.
- **MCP/skill scanner** (`mcpScan.ts`, `GET /api/mcp-scan`, **Protect → MCP Scan**) statically and read-only scans installed MCP server configs and `SKILL.md` skills under `~/.claude` for tool-poisoning, prompt-injection in descriptions, hardcoded secrets (via `scrub.ts` patterns), and suspicious launch commands (via injected `detectSeverity`). Never launches a server or writes a file; results cached ~30s; roots overridable with `CLAUDESEC_MCP_SCAN_ROOTS` (replaces defaults).
- **Config status** — `GET /api/config/status` reports the live ACTIVE / CAUTION / DEFAULT / OFF state and effective (secret-masked) value of each setting, surfaced in **Settings → Configuration Status**. Distinct from `GET /api/config/env`, which only lists env-var presence + defaults.
- **Local Claude Code guards** in `.claude/hooks/*.cjs` (`block-catastrophic.cjs`, `block-sensitive-files.cjs`, `typecheck-on-edit.cjs`, and the enforcement hook `claudesec-enforce.cjs` which supersedes `block-catastrophic.cjs` while keeping its catastrophic-6 floor) protect the working tree when Claude Code runs *in this repo*. They are dependency-free Node built-ins and all fail open.
- **Path alias** `@/*` resolves to the repo root (not `src/`). Configured in both `vite.config.ts` and `tsconfig.json`.

### Connecting Claude Code to the dashboard

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1
export OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:3000/v1/traces
export OTEL_EXPORTER_OTLP_PROTOCOL=http/json
export OTEL_LOG_TOOL_DETAILS=1
```

The `CLAUDE_CODE_ENHANCED_TELEMETRY_BETA` flag enables `claude_code.llm_request` spans with model name and token counts. Without it, only opaque `tool_call/unknown` spans are emitted. `OTEL_LOG_TOOL_DETAILS` adds tool names and input arguments.

### Key features

- **Welcome screen** with auto-setup (`npx claudesec init`) — first-run UX
- **~630 built-in security rules** — prompt injection, secrets, shells, supply-chain, exfiltration, cloud-metadata SSRF, container escape, crypto-mining, privilege escalation
- **Enforcement** — opt-in PreToolUse hook blocks high-severity tool calls pre-execution; `monitor` (default) / `enforce`, server-controlled via the **Enforce** tab
- **MCP/skill scanner** — **Protect → MCP Scan** static scan of MCP servers + skills (`GET /api/mcp-scan`)
- **Claude Code focused** — purpose-built for Claude Code telemetry and security monitoring
- **Process scanner** — detects running Claude Code processes via `ps aux`, kill switch via `DELETE /api/processes/:pid`
- **OTLP forwarding** — transparent proxy to upstream collectors (set `OTEL_FORWARD_URL`)
- **Auto-export** — hourly JSON snapshots to `exports/` (last 24 kept)
- **MCP server** — 11 tools for AI-to-AI interaction (`POST /mcp`)
- **Responsive UI** — drawer sidebar (below `lg`) + bottom tab bar (below `md`) + a11y
- **Docker** — `docker compose up` for one-command deployment

### Security & isolation env vars

| Var | Purpose |
|---|---|
| `CLAUDESEC_TOKEN` | Bearer token for non-loopback API/MCP access; **required** to bind a non-loopback host (server refuses otherwise) |
| `CLAUDESEC_DB` | SQLite path (point throwaway/test instances elsewhere) |
| `CLAUDESEC_ALLOW_RESET` | Must be `1` to permit `POST /api/reset` (data-wipe disabled by default) |
| `CLAUDESEC_MODE` | Enforcement hook mode: `monitor` (default) / `enforce` |
| `CLAUDESEC_HOOKS_BYPASS` | `1` → hook allows everything for one invocation (escape hatch) |
| `CLAUDESEC_ENFORCE_CONFIG` | Path to the mirrored `enforce-config.json` the hook reads |
| `CLAUDESEC_MCP_SCAN_ROOTS` | Colon/comma-separated roots for the MCP/skill scanner (replaces defaults) |

Outbound sinks (`OTEL_FORWARD_URL`, `CLAUDESEC_WEBHOOK_URL`) share a DNS-resolving **SSRF guard** that blocks loopback / private / metadata ranges (re-checked on every retry to defeat DNS rebinding).
