## System overview

ClaudeSec is a local AI agent observability dashboard. It receives OpenTelemetry traces from running AI agents, evaluates every span against a threat detection engine, persists results to SQLite, and streams live updates to a React frontend over Socket.io.

```
Local agents (Claude Code / Copilot CLI / Codex)
  ↓  tails on-disk .jsonl transcripts (default, zero-config)
transcriptWatcher.ts ─┐
                      ├─→ ingestSpan()
Remote / CI agents ───┘   (same pipeline)
  ↑  OTLP JSON (POST /v1/traces)
server/index.ts (Express)
  ├─ Rate limiting (token bucket per IP)
  ├─ Threat detection (detectSeverity)
  ├─ SQLite write (spans, sessions, alerts)
  ├─ Behavioral anomaly detection (per session)
  ├─ Threshold rule evaluation (per session)
  └─ Socket.io broadcast (sessions-update, alerts-update, span-added)
        ↓
   src/App.tsx (React 19 + Tailwind CSS 4)
```

The default local path is the **transcript watcher**, which tails each agent's on-disk session files and needs no configuration. The OTLP endpoint (`POST /v1/traces`) is the path for remote and CI agents ClaudeSec can't read from disk. Both feed the same `ingestSpan()` pipeline, so local and remote activity land in one dashboard.

## Two-process model

ClaudeSec runs as a single Node process but has two logical layers in one repository.

### server/index.ts — backend

- **Express** handles all HTTP: OTLP ingestion at `POST /v1/traces`, REST endpoints under `/api/*`, and static file serving for the built frontend in production.
- **Socket.io** emits real-time events (`sessions-update`, `alerts-update`, `rules-update`, `span-added`) to connected browser clients.
- **better-sqlite3** provides synchronous, embedded SQLite access with no separate database process.
- In development, the backend also hosts a **Vite dev server** (middleware mode) for frontend HMR on the same port.

### src/App.tsx — frontend

- A single React component (no routing) that owns all UI state.
- **Socket.io client** listens for server events and triggers local state updates.
- Dashboard views include timeline, orchestration, alerts, rules, costs, heatmap, search, processes, and bookmarks — each as a dedicated tab component.

## Data flow in detail

### OTLP ingestion

1. The agent sends an OTLP JSON payload to `POST /v1/traces`.
2. The **token-bucket rate limiter** allows 50 RPS with a burst of 200 per IP (configurable via `CLAUDESEC_RATE_LIMIT_RPS` and `CLAUDESEC_RATE_LIMIT_BURST`).
3. A **circuit breaker** rejects new ingestion with `503` when the span table is at 90% of its configured maximum (default 1,000,000 spans; `0` disables the ceiling). Pruning cannot free spans that are still inside the retention window, so the ceiling is sized by the retention profile to stay above the window's own volume.
4. Each span's attributes and name are concatenated into a search string and passed to `detectSeverity()`.
5. The span record (with severity) is written to the `spans` table. An alert row is written to `alerts` if a rule matched.
6. A `span-added` Socket.io event is emitted per span. A `sessions-update` event is emitted once per batch.
7. Behavioral anomaly detection and threshold rule evaluation run asynchronously after the batch.
8. The HTTP response returns `200 { status: "ok" }` immediately after all spans are persisted.

## Threat detection pipeline

### Pattern matching — SEVERITY_RULES

Built-in rules are a static array of `{ pattern: RegExp, severity, label }` objects compiled into `server/detection.ts`. The full set is documented in [Security Rules](/security/rules).

```
detectSeverity(text):
  1. Evaluate custom rules (most recently added first)
  2. Evaluate built-in SEVERITY_RULES in order
  3. Return first match → { severity, matchedLabel, matchedText }
  4. If no match → { severity: "none" }
```

The `text` input is `JSON.stringify(span.attributes) + " " + span.name`.

When a rule matches:
- The `severity` column on the `spans` row is set to `critical | high | medium | low`.
- An `alerts` row is inserted with the rule label and matched text.
- A webhook delivery is fired asynchronously (if configured).

### Sequence engine (stateful, multi-span)

`SEVERITY_RULES` judges one span at a time. On top of it, `server/sequenceRules.ts` runs a
**stateful sequence engine** — it remembers the last few notable actions per trace and matches
*orderings* across them (a credential read followed by a network send, reconnaissance followed by
exfiltration) that no single-span pattern can express. A match produces its own alert whose
`matchedText` carries the rendered **chain** — each matched step, its span, and its timestamp, in
order — and the chain's severity is also carried onto the span that closed it, so that span isn't
stored as `none` while the alert next to it reads high or critical. See
[Security Rules](/security/rules#the-sequence-engine).

### Behavioral anomaly detection

Runs per affected session after each OTLP batch. Does not block the HTTP response.

| Anomaly | Condition | Severity |
|---------|-----------|----------|
| Token spike | Latest span uses >4× session average input tokens, and >2000 tokens | `medium` |
| Threat burst | ≥3 threats in the last 10 spans of a session | `high` |
| Excessive tool calls | >100 total tool calls in a session (fires once, then deduped for 30 minutes) | `low` |
| Off-hours activity | Agent active between 00:00–05:59 local time | `low` |

Each anomaly is deduplicated within a cooldown window (5–60 minutes) to avoid alert flooding.

### Threshold rules

User-defined numeric conditions evaluated per session after every OTLP batch. Stored in the `threshold_rules` table.

Available metrics: `tokens_in`, `tokens_out`, `threat_count`, `span_count`, `high_threat_count`.

Operators: `>`, `>=`, `<`, `<=`, `=`.

A threshold alert fires at most once per `window_min` minutes per session to prevent duplicates.

## SQLite schema

All data lives in a single file at `~/.claudesec/spans.db`, created automatically on first run (the parent directory is created if missing). The resolved absolute path is **logged at boot**, and is overridable with `CLAUDESEC_DB`. The file is gitignored.

| Table | Purpose |
|-------|---------|
| `spans` | One row per OpenTelemetry span. Primary store. |
| `sessions` | One row per trace ID. Auto-created on first span for a trace. |
| `alerts` | Security alert rows written when a rule matches or a behavioral anomaly fires. |
| `annotations` | Free-text investigation notes attached to a `spanId`. |
| `span_tags` | Short labels attached to spans for triage workflows. |
| `threshold_rules` | User-configured numeric alert conditions. |
| `webhook_deliveries` | Log of every webhook delivery attempt (last 500 rows). |
| `config` | Key-value store for runtime configuration (webhook URL, retention settings). |
| `suppressions` | Active rule snoozes — rules suppressed until a given timestamp. |
| `operator_audit_log` | Append-only record of config-mutating actions; **hash-chained**. |
| `enforce_log` | Persisted enforcement would-block/block feed; capped at 500 and **hash-chained**. |
| `span_chain_tombstones` | Chain position, hashes and timestamp of every deleted span — the link a pruned span leaves behind. |
| `spans_fts` | FTS5 external-content index over `spans(spanId, name, attributes)`. |

### Durability & lifecycle

- **WAL + `busy_timeout`.** The database runs in WAL mode (concurrent reads during writes); `busy_timeout = 5000` makes a momentarily-contended writer wait up to 5s for the lock rather than fail with `SQLITE_BUSY`.
- **Graceful shutdown.** On `SIGTERM` / `SIGINT` the server stops accepting connections, checkpoints the WAL back into the main file, and closes the handle — so an abrupt stop can't leave a half-applied WAL.
- **Online binary backups.** A consistent `.db` snapshot is written to `~/.claudesec/backups/` (`0600`, most-recent 7 retained) shortly after boot and daily thereafter, using SQLite's online backup API. This is distinct from the hourly human-readable JSON auto-export in `exports/`.
- **Hash-chained records.** `operator_audit_log`, `enforce_log` and `spans` all carry a per-row SHA-256 hash chain; `GET /api/audit/verify` recomputes them. The boundaries a chain cannot see about itself — how many rows there should be, and where the chain should end — live in an **Ed25519-signed tail anchor** kept outside the database, so an emptied table and an empty table are different answers. Detection, never prevention; see [what it proves](/api-reference/audit-log#what-the-integrity-mechanism-actually-proves) before relying on it.

### The spans chain and retention

A hash chain is a statement about a complete sequence; retention deliberately destroys parts of that sequence. Delete a span from the middle and the next span's `prevHash` points at something that no longer exists — after a few months every verification would fail for entirely legitimate reasons, and "broken because retention ran" would be indistinguishable from "broken because someone deleted evidence".

Re-threading the survivors (what the two small capped logs do) is not an option here: it would rewrite 269,000 hashes on every sweep and destroy the original hashes, which are the things a third party may already have been handed. Chaining per session does not help either, because the count-based prune deletes the oldest spans regardless of session.

So ClaudeSec **keeps the link when it deletes the payload.** Deleting a span leaves a tombstone in `span_chain_tombstones` holding only its chain position, its hash, its predecessor's hash and when it went — around 160 bytes against roughly a kilobyte for the span itself. The chain is verified over the union of live spans and tombstones ordered by position, so it stays continuous and complete forever while the data itself is genuinely gone (which data-minimisation obligations require). Retention still deletes what it must; what it stops deleting is the proof.

That inverts the failure mode into the useful one: a missing position with **no** tombstone is not "retention ran", it is an unaccounted deletion, and the verifier reports the exact position. The tombstone is evidence in the other direction too — hand it a span's content and it will say whether that is the span that used to sit there, without ever having stored the content.

The tombstone is written by a SQLite trigger rather than by the pruning code, so it fires for every delete against the file — including one typed into `sqlite3`. Tombstones accumulate for the life of the install (a few megabytes per hundred thousand spans ever ingested), which is the price of a record that can still answer "was anything removed" after the data is gone.

### Import-safe startup

`server/index.ts` is **side-effect-free on import**: merely importing the module starts no HTTP listener, schedules no timers, and writes no hook-config mirrors. The server only autostarts — and only then derives the hook artifacts (protected-paths, rules snapshot, enforce mode) from the database — when the file is the process entry point. Set `CLAUDESEC_NO_AUTOSTART=1` to force import-only behaviour regardless of how the module is invoked.

### FTS5 full-text index

`spans_fts` uses the `unicode61` tokenizer with diacritic removal, and is declared as an **external-content** index (`content='spans'`, `content_rowid='rowid'`). It therefore stores search terms only, never a second copy of the span text — the values themselves are read back out of `spans` by rowid, which is why every index row is pinned to the rowid of the span it describes.

It is kept in sync by `AFTER INSERT`, `AFTER DELETE`, and `AFTER UPDATE` triggers on `spans`, so retention pruning removes a span's indexed content along with the span itself. The delete and update triggers use FTS5 delete-command rows carrying the old values, because an external-content index cannot look up the row it is removing. A one-time, chunked, resumable rebuild runs on server startup to convert and backfill a database created before this layout.

## Session health scoring

ClaudeSec currently exposes two related score paths:

1. **`GET /api/sessions/:traceId/health`** uses `computeHealthScore(traceId)` with:
   `100 - (high*15) - (medium*8) - (low*3) - min(alerts*10, 30)` and returns `score + grade`.
2. **`GET /api/sessions`** includes inline `riskScore` and `healthScore` derived from weighted threat counts, alert weight, and threat-density.

The dashboard badge coloring uses the inline `healthScore` (`green >= 80`, `yellow 50-79`, `red < 50`).

## Rate limiting

Token-bucket algorithm, one bucket per client IP.

| Parameter | Default | Env override |
|-----------|---------|--------------|
| Sustained rate | 50 RPS | `CLAUDESEC_RATE_LIMIT_RPS` |
| Burst capacity | 200 requests | `CLAUDESEC_RATE_LIMIT_BURST` |
| Max spans per batch | 500 | `CLAUDESEC_MAX_SPANS_BATCH` |

When the limit is exceeded the server responds with `429 Too Many Requests` and a `Retry-After` header.

Stale buckets (idle for >5 minutes) are evicted every 60 seconds.

## Graph API (headless)

The graph endpoints (`GET /api/graph`, `/api/graph/mermaid`, `/api/graph/dot`) remain available as a headless API for programmatic access and export. They return span dependency data with Dagre-computed positions, suitable for rendering in external tools (Mermaid, Graphviz) or custom integrations. There is no graph UI tab in the dashboard.

The graph renders only the **most-recent N events** — bounded by `CLAUDESEC_GRAPH_LIMIT` (default 2000) — so it stays fast as the database grows. Older events are **not** deleted; they remain available through Search and Sessions. See [Data retention](/explanation/retention) for the full capacity model.
