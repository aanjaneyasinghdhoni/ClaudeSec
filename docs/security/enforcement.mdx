Detection tells you what an agent *already did*. **Enforcement** can stop a tool call *before it runs* — using the same rule library, wired into Claude Code as a **PreToolUse hook** (`claudesec-enforce.cjs`).

<Warning>
  **Enforcement is opt-in. Out of the box, ClaudeSec only observes — it blocks nothing.** There is **zero pre-execution blocking** until you [install the hook](#install-the-hook). Even then, it reaches **Claude Code only**, is **monitor by default**, and is **fail-open** (see below). It raises the bar for an agent; it is not an OS sandbox or a hard guarantee.
</Warning>

When Claude Code is about to run a `Bash`, `Edit`, `Write`, `Read`, or `WebFetch` tool call, it passes the proposed payload to the hook on stdin. The hook evaluates that payload and either allows it (exit 0) or denies it (exit 2, with a reason shown to the agent). Several **always-on floors** block in either mode — the [catastrophic floor](#the-catastrophic-floor), the [SSRF-on-fetch](#ssrf-on-fetch) cloud-metadata tier, [self-protection](#self-protection-the-control-plane) of the enforcement control plane, the live-secret edit check, and your [protected paths](#protected-paths-always-on) (including a [sane default set](#a-sane-default-set-out-of-the-box)) — while the broader high- and critical-severity rules block only once you switch to [enforce](#modes).

### What the hook actually inspects (block actions, not edits)

The hook does **not** scan the body of every file you write against the rule library — that would block legitimate edits to security code, attack-pattern docs, or secret-shaped test fixtures. Instead it gates on the **action and its target**:

- **`Bash`** — the full command is evaluated against the rule engine **and** the always-on [catastrophic floor](#the-catastrophic-floor). This is the one tool whose entire payload is matched against the rules.
- **`Edit` / `Write` / `MultiEdit`** — the block decision is the **file path + action**, checked against your [protected paths](#protected-paths-always-on). The only thing the hook reads from the file *content* is a tiny, high-confidence **live-secret floor**: it refuses to write an unambiguous live credential (an AWS key, a GitHub token, a private-key block, …), with documentation placeholders (e.g. AWS's canonical `AKIAIOSFODNN7EXAMPLE`) allowlisted. The static body of the code being written is **never** matched against the broader rule set.
- **`Read`** — runs only the protected-paths floor, so a read of a protected secret can be denied before it happens. It is never matched against the command rules.
- **`WebFetch`** — runs the [SSRF-on-fetch floor](#ssrf-on-fetch) so a fetch aimed at a cloud-metadata or internal host is denied before the request leaves the machine.

This is the key distinction from **detection**: the dashboard's threat detection still inspects full span content, so you keep visibility into everything an agent did even when the enforcement floor, by design, only blocks on the path + action.

<Warning>
  The hook is the **Claude Code layer** — it is agent-specific and bypassable (see [Bypass](#bypass)), **not** an OS-level sandbox. It also **fails open**: any error, missing config, or unparseable input results in *allow*, so a broken enforcement config can never lock you out. For agents that aren't Claude Code, the same rules are enforced at the **MCP wire level** — see [Cross-agent enforcement](#cross-agent-enforcement-mcp-proxy).
</Warning>

## Install the hook

The hook is **not registered for you** — Claude Code only runs a PreToolUse hook that exists in its settings. One command wires it up. From a clone:

```bash
node cli/init.mjs install-hook
```

This is **consent-gated**: before it touches anything, it prints the exact target file and the exact JSON it will add, then waits for a `y/N` confirmation (pass `--yes` to skip the prompt in a trusted script). Here's what it does, in order:

1. **Builds the rules snapshot locally.** It runs `scripts/build-enforcement-rules.ts` against your in-repo rule source to generate a fresh `rules-enforcement.json`. This is a pure local build — **no network call, ever** — so the hook blocks exactly the rules in *your* checkout.
2. **Copies the hook + snapshot** into `~/.claudesec/hooks/` (`claudesec-enforce.cjs` and its `rules-enforcement.json`, side by side).
3. **Backs up your settings first.** If `~/.claude/settings.json` already exists, it's copied to a timestamped `.bak-<ts>` before any write.
4. **Merges PreToolUse entries** into `~/.claude/settings.json` — one matching `Bash`, one matching `Edit|Write|MultiEdit|NotebookEdit`, one matching `Read` (so a protected path is also denied on read), and one matching `WebFetch|WebSearch` (so an [SSRF](#ssrf-on-fetch) to a cloud-metadata / internal host is denied before the request leaves the machine). Every other key, hook, and matcher in your settings is preserved untouched.
5. **Logs the action** to `~/.claudesec/install.log`.

It is **idempotent**: re-running refreshes the copied hook and snapshot and never duplicates the settings entries. Restart Claude Code afterward so it loads the hook.

<Note>
  Installing the hook turns on **pre-execution blocking**, but the honest framing still holds: the hook is **fail-open by design** — if it errors, the tool call is allowed through. The catastrophic floor always blocks; rule-based blocking only takes effect once enforce mode is also on (see [Modes](#modes)).
</Note>

### Uninstall

```bash
node cli/init.mjs uninstall-hook            # remove only ClaudeSec's settings entries
node cli/init.mjs uninstall-hook --purge    # also delete ~/.claudesec/hooks/
```

Uninstall removes **only** ClaudeSec's own four PreToolUse entries — everything else in your settings stays. It backs up `settings.json` first, the same way install does. Add `--purge` to also delete the copied hook and snapshot under `~/.claudesec/hooks/`. Restart Claude Code to drop the hook.

## Modes

The hook runs in one of two modes, and **`monitor` is the default**:

| Mode | What it does |
|------|--------------|
| `monitor` (default) | Logs every "would-block" to the dashboard but **never blocks** — except the always-on floors: the *catastrophic floor*, the *cloud-metadata SSRF* tier, *self-protection* of the control plane, the *live-secret* edit check, and your *protected paths* (defaults included). |
| `enforce` | Actually **denies** high- and critical-severity command / file tool calls, in addition to every always-on floor. The critical tier is active secret *exfiltration*. |

The broader rule library — and any **custom regex rules** you add in the dashboard — only ever *blocks* in `enforce` mode. Custom rules follow the same convention as the built-ins: they **detect by default**, and in `enforce` mode a **high- or critical-severity** custom rule also **blocks** (low/medium custom rules stay detect-only). The server mirrors your custom rules into the hook's `rules-enforcement.json` snapshot so the hook enforces the same set. To always-block a specific file or directory in *either* mode, use [protected paths](#protected-paths-always-on) instead.

### The catastrophic floor

A set of bash patterns **always** block, in either mode — the unambiguous "you almost certainly did not mean this" commands, plus two high-precision secret-exfiltration patterns:

- `rm -rf` against the filesystem root (`/`), including the `--no-preserve-root` form that exists only to defeat that guard
- recursive deletes of a critical system tree or the whole home — `/etc`, `/boot`, `/usr` (and `/usr/{bin,lib,sbin,…}`), `/var` (and `/var/{lib,log,db,…}`), `~` / `$HOME`. Developer territory is **carved out** so routine cleanup is never walled off: `/usr/local` (Homebrew, global npm), `/var/folders` and `/var/tmp` (the macOS `$TMPDIR`), and any sub-path like `~/project` stay allowed
- fork bombs
- piping a remote download straight into a shell (`curl … | sh` / `wget … | sh`)
- reverse shells via `/dev/tcp` and `/dev/udp`, and netcat reverse shells (`nc -e` / `nc -c`)
- formatting a filesystem (`mkfs.*`)
- overwriting or redirecting onto a raw disk device (`dd of=/dev/…`, `> /dev/sda`), including a single partition (`/dev/sda1`, `/dev/nvme0n1p2`)
- common Windows destructive commands — `format <drive:>`, `diskpart`, `bcdedit`, `del /f /q /s`, `rd /s`, deleting volume shadow copies (`vssadmin delete shadows`), secure-wiping free space (`cipher /w`), and wiping the event log (`wevtutil cl`). Each is anchored so the ordinary dev word (`npm run format`, a `formatter`) never matches
- reading a secret and piping it to the network in one command (`cat ~/.ssh/id_rsa | curl …`)
- uploading a secret file directly to the network (`curl -d @.env https://…`)

The last two are deliberately narrow — they fire only when a command both reads a known secret and ships it off-machine — so they block this always, even in monitor mode, without flagging ordinary network calls. Every floor pattern is RE2-compiled and proven **linear-time** by a self-test, so a long or adversarial command line can never cause catastrophic regex backtracking.

### SSRF on fetch

When the hook is installed, a `WebFetch` aimed at a server-side-request-forgery target is blocked before the request leaves the machine — the classic agent-SSRF where a model is talked into fetching `http://169.254.169.254/latest/meta-data/…` and exfiltrating a cloud credential.

- **Cloud-metadata and link-local addresses are blocked in *either* mode** (mode-independent floor): the whole `169.254.0.0/16` and IPv6 `fe80::/10` ranges, plus the GCP metadata hostnames (`metadata`, `metadata.google.internal`, `metadata.goog`). These have no legitimate `WebFetch` use.
- **Loopback and private (RFC1918) ranges are blocked in `enforce` mode** — `127.0.0.0/8`, `10/8`, `172.16/12`, `192.168/16`, `::1`. Set `CLAUDESEC_ALLOW_LOCAL_FETCH=1` to opt out (e.g. when an agent must legitimately fetch a local dev server); cloud-metadata stays blocked regardless.

<Warning>
  **Honest limitation — DNS rebinding.** The hook is synchronous and matches on the URL's literal host, so a **public hostname that resolves to an internal IP** is not caught here. The server-side SSRF guard (`server/ssrf.ts`), which DNS-resolves every host at fetch time, is the backstop for the outbound paths *it* controls (webhook / forward / judge); the hook's fetch floor catches the literal-address case that those server paths never see.
</Warning>

### Symlink-aware protected paths

Protected-path checks resolve the **realpath** of a target before matching, so a symlink that points into a protected tree is blocked even though its literal spelling doesn't name the protected path. For a file that doesn't exist yet (a fresh `Write`), the hook resolves the nearest existing ancestor directory and re-appends the new tail, so you can't slip a write past the floor through a symlinked parent directory.

<Note>
  **Honest limitation — TOCTOU.** Realpath resolution happens at check time. A path that is swapped between the hook's check and the actual write (a time-of-check/time-of-use race) is a residual gap inherent to any pre-exec hook — this raises the bar, it is not an OS-level guarantee.
</Note>

### Self-protection (the control plane)

An agent must never be able to edit the enforcement control plane and unhook the enforcer. A **self-protection floor** therefore **always blocks** — in either mode — any agent tool call (a `Write`/`Edit`, or a Bash redirect) that targets:

- the whole `~/.claudesec/hooks/` directory — the installed hook, `enforce-config.json`, the `rules-enforcement.json` snapshot, `protected-paths.json`, and the `audit-key`;
- the Claude Code settings files that register the PreToolUse hook — both the **home-dir** `~/.claude/settings.json` / `settings.local.json` **and** the **project-level** `./.claude/settings.json` / `settings.local.json` in the directory the agent is working in. Claude Code honors project-level settings too, so an agent could otherwise register a competing hook to displace the enforcer; both scopes are guarded.

This guards **agent** tool calls only. The ClaudeSec server writes these same files from its own process on boot — a different process, not subject to this floor.

### Protected paths (always-on)

Beyond the catastrophic floor, you can mark **specific files or directories as protected** — a per-user floor that **always blocks**, in either mode, exactly like the catastrophic floor. Add them in **Protect → Rules → Protected paths** (or via `POST /api/protected-paths`). A protected entry is denied on **read, write, edit, and delete** — the hook registers a `Read` matcher alongside the write/edit matchers, so any Claude Code tool call whose **target path** or **Bash command** (e.g. `cat`/`rm`) references a protected entry is blocked before it runs.

#### A sane default set, out of the box

A fresh install protects nothing if the list is empty, so ClaudeSec ships a small, conservative set of **default protected paths** — the high-value credential stores an agent should never read or overwrite:

| Default | What it protects |
|---|---|
| `~/.ssh` | SSH private keys |
| `~/.aws/credentials` | AWS credentials |
| `~/.config/gcloud` | gcloud config + tokens |
| `~/.kube/config` | Kubernetes cluster credentials |
| `~/.npmrc` | npm auth tokens |
| `.env`-style secret files | dotenv secrets, matched **by shape** — `.env`, `.env.local`, `.env.production`, … |

The dotenv default carves out the well-known committed templates — `.env.example`, `.env.sample`, `.env.template`, `.env.dist`, `.env.tpl` — so editing scaffolding that holds no real credentials is never blocked. It matches the file **target** only (a read/write/edit of a real `.env`), not a free-form Bash command, so a plain `cat .env` isn't walled off by this default — the always-on exfil floor already covers the dangerous "read a secret and pipe it to the network" case.

These defaults are **deliberately minimal** and **user-removable** — they aren't pinned. Your own entries are merged on top, and you can drop any default from the list if it gets in the way. Both the hook and the MCP proxy load the same merged set, so the defaults apply to a cross-agent call too.

- Matching is a case-insensitive substring of the file *target* (`file_path` / `path` / `notebook_path`) or the Bash command — **never** the edit *content*, so editing a file that merely *mentions* a protected path is fine. A leading `~` and a standalone `$HOME` / `${HOME}` expand to your home dir; arbitrary shell variables, globs, and command substitution are not resolved (a static hook's inherent limit — server-side detection remains the backstop).
- Protected paths are **detection-independent**: they don't depend on any rule and ignore enforce mode.
- They only take effect through the **installed hook**. The server mirrors your list to the hook's directory automatically; if you've added protected paths but the hook isn't installed, the dashboard and server log say so (nothing will block until you [install the hook](#install-the-hook)).

In `monitor` mode these two floors — the catastrophic floor and protected paths — are the **only** things that block; everything else is logged and allowed.

## Turning it on

The **server is the source of truth.** The recommended workflow is monitor first, then enforce:

1. **Watch in monitor mode.** Run normally (the default). Open the **Enforce** dashboard tab and let your agents work. Every rule that *would* have blocked appears in the would-block feed, so you can confirm the rules match real activity without disrupting anything.
2. **Flip to enforce.** When the would-block feed looks right, switch the mode to **enforce** from the **Enforce** tab. The server persists the mode and mirrors it to `enforce-config.json`, which the hook reads on each call.

You can also set the mode through the API:

```bash
# Read current mode + overrides:
curl http://localhost:3000/api/enforce/config

# Switch to enforce:
curl -X PUT http://localhost:3000/api/enforce/config \
  -H 'Content-Type: application/json' \
  -d '{"mode":"enforce"}'
```

Or set `CLAUDESEC_MODE=enforce` in the hook's environment.

### Mode precedence

The hook resolves its mode with a **fixed, deterministic order**. The first layer that supplies a valid `monitor`/`enforce` value wins:

1. **`enforce-config.json`** — the file the dashboard toggle writes (highest precedence).
2. **`CLAUDESEC_MODE`** — the environment variable.
3. **`monitor`** — the default when neither of the above is set.

The consequence trips people up: **the config file wins over the env var.** If you set `CLAUDESEC_MODE=enforce` but `enforce-config.json` says `monitor`, the hook runs `monitor` — the env value is ignored. The **Enforce** tab surfaces this directly: when the env var is being overridden by the config file, it shows a warning naming both values, so a stale config can't silently leave you in the wrong mode.

<Note>
  Per-rule overrides let you promote an `alert` rule to `block` (or demote a `block` rule to `alert`) without rebuilding the rule snapshot — `PUT /api/enforce/config` accepts an `overrides` map of `ruleLabel → "alert" | "block"`.
</Note>

### Reading the Enforce tab honestly

The **Enforce** tab is built to never show a comforting green when nothing can actually be blocked. It separates three distinct truths, all served by `GET /api/enforce/config`:

- **Configured mode** — the dashboard toggle (`monitor`/`enforce`).
- **Effective mode + winning source** — what the hook *actually* runs after the precedence above, labelled with where it came from (`enforce-config.json`, `CLAUDESEC_MODE env`, or the monitor default). When the configured toggle and the effective mode disagree, the tab calls it out.
- **Hook registration** — whether a PreToolUse entry running our enforcer is present in your Claude Code settings (`yes` / `no` / `unknown`), and in which scopes (user / project / project-local).

There is **no false green**. The standing "Blocking enabled (fail-open by design)" state appears **only** when enforce is the effective mode **and** a hook is registered. If no hook is registered, the tab warns that it can neither block nor observe tool calls through the hook — a live would-block feed proves the hook *fired*, never that blocking is correctly wired. Inside a container the host's settings aren't visible, so registration reads `unknown` (a neutral note, not a misleading `no`) — container detection is Docker-only.

## The would-block / block feed

Every decision the hook reports streams to the **Enforce** tab over Socket.io and is also available at:

```bash
curl 'http://localhost:3000/api/enforce-log?limit=100'
```

The feed is **persisted to SQLite** (a capped table, pruned to the most recent 500 events) and **tamper-evident** — each event is hash-chained to the one before it, the same way the [operator audit log](/api-reference/audit-log) is, so it survives a server restart and any later edit to an earlier row is detectable. **Settings → Configuration Status** also summarizes recent enforcement activity (events in the last 24h) alongside the live mode.

## Bypass

Need to run something the hook would block, just once? Set the escape-hatch variable for that invocation:

```bash
CLAUDESEC_HOOKS_BYPASS=1 claude ...
```

With it set, the hook allows everything and exits — but it is no longer silent. Before allowing the call, the hook records a **bypass event** in the enforcement feed (label `Enforcement bypassed (CLAUDESEC_HOOKS_BYPASS=1)`, with the tool name and a short summary of what was allowed), so an operator or incident responder can see that enforcement was disabled and for what. This recording is best-effort and fail-open: if the dashboard is unreachable the call is still allowed, never blocked or hung.

This makes accidental and operational bypasses auditable. It is **not** a tamper barrier: a same-UID attacker who can set `CLAUDESEC_HOOKS_BYPASS=1` can also unregister the hook or tamper further. Because enforcement is a Claude-Code hook, removing or not registering the hook also disables it entirely — which is exactly why the honest framing above matters: enforcement raises the bar for an agent, it does not sandbox the host.

<Warning>
  `CLAUDESEC_HOOKS_BYPASS=1` is checked by the hook before any rule evaluation — including the catastrophic floor. Any subprocess spawned by an agent that inherits this variable will also bypass all enforcement. If you set it in a shell session where an agent is running, every tool call in that session is allowed through, regardless of mode or rule severity. Treat it accordingly: use it for a single targeted invocation, then unset it.
</Warning>

## Cross-agent enforcement (MCP proxy)

The PreToolUse hook only reaches **Claude Code**. To enforce the *same* rules for **any** MCP-speaking agent — Codex, Copilot, Claude Desktop — ClaudeSec ships a **cross-agent MCP enforcement proxy**: a stdio gateway that wraps a downstream [MCP](https://modelcontextprotocol.io) server and gates every `tools/call` against the same `rules-enforcement.json` + `enforce-config.json`.

The proxy speaks raw [JSON-RPC 2.0 over stdio](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports). It is a transparent pipe for `initialize`, `tools/list`, `resources/*`, `prompts/*`, `ping`, and all responses; it intercepts **only** `tools/call`. The hook and the proxy share a single evaluation core (`server/enforceEval.ts`), so a `tools/call` hits the **same floors and the same rule set** the hook applies to a Claude Code tool call — a behavioral parity test (`tests/enforceParityTest.ts`) pins the proxy's verdict to the hook's so they cannot drift. For each call the proxy detects the tool **shape** and extracts the right text, exactly as the hook does:

- **command-shaped** tools (`bash`/`sh`/`exec`/`run_command`/…) → the **raw command string** is pulled out of its argument and matched. This matters: the catastrophic floor's patterns are anchored to a command boundary, so wrapping the command in a JSON blob (`{"command":"rm -rf /"}`) would destroy those anchors and silently miss `rm -rf /`. The proxy evaluates the unwrapped command, not the serialized blob.
- **edit-shaped** tools (`edit`/`write`/`create_file`/`apply_patch`/…) → the **target path** feeds the self-protection and protected-paths floors; the **new content** is checked only by the minimal live-secret floor — never the broad rule set.
- **fetch-shaped** tools (any call carrying a `url`/`uri`/`endpoint` argument) → the URL feeds the **SSRF-on-fetch floor** (see below).
- anything else → the serialized arguments are matched against the rule engine.

It then evaluates the extracted text:

- **`enforce`** + a high- or critical-severity `block` rule (or any always-on floor) matches → the call is **not** forwarded; the agent gets a `tools/call` result with `isError: true` and an explanatory message (a clean, model-readable refusal — not a transport error), and a would-block is logged to the dashboard.
- **`monitor`** (default) + match → logs a would-block, then forwards normally.
- no match → forwards.

Mode is resolved per call (`enforce-config.json` → `CLAUDESEC_MODE` → `monitor`), so dashboard toggles take effect live. Like the hook, it **fails open** (any parse/proxy error forwards the original message) and honors `CLAUDESEC_HOOKS_BYPASS=1` (forward everything).

#### SSRF over the proxy, too

The same [SSRF-on-fetch floor](#ssrf-on-fetch) the hook applies to a Claude Code `WebFetch` is enforced **server-side in the proxy** for any fetch-shaped MCP tool. A non-Claude-Code agent (Codex, Copilot, Claude Desktop) routed through the proxy can no longer reach a cloud-metadata or internal host that the hook would have blocked — cloud-metadata / link-local is blocked in either mode, loopback/private in `enforce` (with the same `CLAUDESEC_ALLOW_LOCAL_FETCH` opt-out). The DNS-rebinding limitation is identical: the classifier matches the literal host and does not resolve a public name.

<Note>
  **Catastrophic-floor behavior differs between the hook and the proxy.** The proxy evaluates the *same* floor patterns against the same raw command — but they are gated by mode. The PreToolUse hook blocks the catastrophic floor in *either* mode; the proxy only **logs** a would-block in `monitor` (default) and **denies** the call in `enforce`. This is a deliberate proxy contract, not a coverage gap (the parity test verifies the trigger matches the hook's exactly). If you are gating a non-Claude-Code agent and want the catastrophic floor to block, set the mode to `enforce`. The cloud-metadata SSRF tier is the exception — it is mode-independent and blocks in either mode on both layers.
</Note>

### Wiring an agent

Point the agent's `mcpServers` entry at the proxy instead of the real server. Wherever you would have launched `<real-server> <args...>`, launch:

```
claudesec mcp-proxy -- <real-server> <args...>
```

For example, to gate a filesystem MCP server in an agent's MCP config:

```json
{
  "mcpServers": {
    "filesystem": {
      "command": "claudesec",
      "args": [
        "mcp-proxy", "--",
        "npx", "-y", "@modelcontextprotocol/server-filesystem", "/work"
      ],
      "env": { "CLAUDESEC_MODE": "monitor" }
    }
  }
}
```

The agent now talks to ClaudeSec, which transparently relays to (and gates) the real `server-filesystem`. Tool discovery (`tools/list`) is unchanged, so the agent sees exactly the same tools. Set `CLAUDESEC_MODE: "enforce"` (or flip the mode from the **Enforce** tab) when you're ready to block.

<Note>
  The proxy posts its would-blocks to `/api/enforce-log` (port from `CLAUDESEC_PORT` → `PORT` → 3000), so MCP-level decisions show up in the **same** Enforce dashboard feed as the hook's.
</Note>

## How the rules are built

Both the hook and the MCP proxy compile their block-set from a `rules-enforcement.json` snapshot, regenerated from the live rule engine by `scripts/build-enforcement-rules.ts` (run: `tsx scripts/build-enforcement-rules.ts`). A rule blocks only if its effective action (snapshot action, possibly overridden) is `block`. The shared evaluation core lives in `enforceEval.ts` (imported by the proxy); the hook reproduces the same semantics dependency-free in `.claude/hooks/claudesec-enforce.cjs`. See [Security Rules](/security/rules) for the underlying rule library.

## Limitations & threat model

ClaudeSec's enforcement is built to stop a **misbehaving agent** — a model that has been talked into running a destructive command, exfiltrating a secret, or fetching a cloud-metadata endpoint. It is **not** a defense against a determined **same-user attacker**. The hook, the proxy, and the dashboard all run as *you*, on *your* machine, with *your* permissions. A process running under the same user account has the same reach over the same files — there are inherent ceilings, and we'd rather state them plainly than imply a guarantee the design can't make.

- **Enforcement is best-effort and fail-open.** Every layer — hook and proxy — allows the call through on any error, missing config, or unparseable input, so a broken config can never lock you out. It covers the Claude Code PreToolUse hook and the MCP proxy. It does **not** intercept arbitrary egress: a process the agent spawns outside those two chokepoints (a raw socket, a non-proxied tool, a child process that doesn't inherit the hook) is not gated. This raises the bar; it is not an OS sandbox.

- **Mutating enforcement routes are loopback-trusted.** On `localhost` the API requires no token (that is the local-first default), so a **same-host process** could call the enforcement API to change the **mode** (flip `enforce` back to `monitor`) or clear **user-added** protected paths. What it **cannot** turn off, in any mode, are the **always-on floors**: the catastrophic floor, self-protection, the live-secret edit floor, the cloud-metadata SSRF floor, and the **default** protected paths. Those block regardless of mode and regardless of the configured rule actions — flipping to `monitor` does not disarm them.

- **The audit log is tamper-evident, not tamper-proof.** The hash chain detects in-place edits, reordering, and deletion (it pinpoints the first broken row), and reset detection catches a wholesale wipe. But a same-user attacker who can recompute the entire chain — and read the local HMAC key, which now lives under the self-protected hooks directory (raising the bar, not eliminating it) — can forge a self-consistent history. **Truncating the newest rows off the tail** is the residual gap the chain cannot detect on its own. See the [Audit Log API](/api-reference/audit-log#how-tamper-evident-works) for the full treatment.

- **DNS rebinding and symlink TOCTOU remain known gaps.** The synchronous hook (and proxy) classify a fetch URL by its **literal host**, so a public hostname that *resolves* to an internal IP is not caught at this layer — the server-side, DNS-resolving SSRF guard (`server/ssrf.ts`) is the backstop for the outbound paths *it* controls. And protected-path realpath resolution happens at check time, so a path swapped between the check and the write (a time-of-check/time-of-use race) is an inherent limit of any pre-exec hook.

If your threat model includes a hostile process running as your own user, layer ClaudeSec under an OS-level sandbox, separate user account, or container boundary — enforcement is one defense-in-depth control, not the whole perimeter.
