## How rules work

Every span — whether tailed from a local transcript or sent via OTLP to `POST /v1/traces` — is evaluated against the security rule engine. The engine concatenates the span name and all attributes into a single string and tests it against each rule's regular expression in priority order:

1. **Custom rules** are checked first (most recently added = highest priority).
2. **~639 built-in rules** are checked if no custom rule matches.

The first matching rule determines the span's severity level (first-match-wins). If no rule matches, the severity is `none` and the span is treated as benign.

A matched span results in:
- The span being colored by severity in the Timeline and spans list (yellow/orange/red).
- An **alert** row written to the `alerts` table and shown on the [Alerts](/security/alerts) screen.
- A Socket.io `alerts-update` event broadcast to all connected clients.
- A webhook delivery and desktop notification for HIGH- and CRITICAL-severity alerts (if configured / permitted).

<Note>
  Custom rule patterns are compiled with **RE2** (linear-time, ReDoS-safe) on the server detection path, so a malformed or adversarial regex cannot hang the server. Note: the dependency-free PreToolUse hook evaluates custom block rules with the native JavaScript regex engine, not RE2 — input is capped at 64 KB per call as a backstop, but a pathological pattern could still stall that single hook invocation.
</Note>

## Severity levels

| Level | Color | Meaning |
|-------|-------|---------|
| `critical` | Rose (`#f43f5e`) | Active **exfiltration** — a confirmed secret / credential / `.env` being transmitted off the machine (piped to `curl`/`wget`/`nc`, `scp`/`rsync`/`sftp` to a remote, posted via `requests`, or a key literal in a POST body) |
| `high` | Red (`#ef4444`) | Immediate risk — system compromise, data destruction, prompt injection, a secret merely *present* in a file or read locally |
| `medium` | Orange (`#f97316`) | Elevated risk — sensitive file access, credential-adjacent activity |
| `low` | Yellow (`#eab308`) | Noteworthy — potentially legitimate but worth reviewing |
| `none` | Gray | No threat detected |

<Note>
  `critical` is strictly about **transmission**, not presence. A secret, key, or `.env` sitting in a file — or being read locally — stays `high`. It becomes `critical` only when it is sent to a network sink. This keeps the top tier conservative and low-noise.
</Note>

## Built-in rules

### CRITICAL severity

The highest tier — reserved for active secret **exfiltration**. Each rule pairs a credential, private key, or `.env` with a network sink (a pipe to `curl`/`wget`/`nc`, an `scp`/`rsync`/`sftp` to a remote host, a `requests.post`, or a key literal inside a POST). `.env.example` (the conventional non-secret template) is deliberately excluded. A representative selection:

| Rule label | What it catches |
|------------|-----------------|
| `.env` / env vars piped to exfil tool | `env`/`printenv` output piped to `curl`/`wget`/`nc` |
| `.env` file read piped to network sink | `cat .env` (or `.env.local`/`.env.production`) piped to `curl`/`wget`/`nc` |
| curl exfil of `.env` file | `.env` sent via `curl --data`/`--upload-file`/`-T` |
| `.env` file rsync to remote host | `.env` rsync'd to `user@host:` |
| AWS credentials file piped to network sink | `~/.aws/credentials` piped to `curl`/`wget`/`nc` |
| SSH private key / PEM piped to network sink | `id_rsa`/`id_ed25519`/`*.pem` read and piped to a network tool |
| SSH private key remote copy | `scp` of an `~/.ssh/id_*` key to a remote host |
| curl upload of SSH private key / PEM | private key sent via `curl --upload-file`/`-T` |
| credential file base64-piped to curl/wget | a secret base64-encoded then piped to `curl`/`wget` |
| private key PEM in curl POST body | a `-----BEGIN … PRIVATE KEY-----` block inside a `curl` POST |
| API key literal in curl POST to external host | `AKIA…`/`sk-ant-…`/`ghp_…`/`AIza…` in a `curl` POST to a non-local host |
| Python reads credential file then POSTs to network | `open(".env"/credentials/key)` followed by `requests.post`/`urlopen` |
| scp / sftp of secrets or cert file to remote host | `.env`/`.pem`/`.key`/`.p12` copied to a remote |
| netcat file transfer to remote host | a file streamed outbound over `nc`/`netcat` to a remote |

Critical rules are blocked in `enforce` mode alongside HIGH rules; in `monitor` mode they alert only — with one exception: two high-precision exfiltration patterns (read-a-secret-and-pipe-it-to-the-network, and upload-a-secret-to-the-network) sit on the always-on catastrophic floor and block in either mode once the hook is installed (see [Enforcement](/security/enforcement)).

### HIGH severity

| Rule label | Pattern | What it catches |
|------------|---------|-----------------|
| Recursive root deletion | `rm\s+-rf\s+[\/\\]` | `rm -rf /` or `rm -rf \` style commands |
| Remote code execution via curl | `curl\s+.*\|\s*(ba)?sh` | `curl URL | bash` one-liners |
| Remote code execution via wget | `wget\s+.*\|\s*(ba)?sh` | `wget URL | bash` one-liners |
| SQL destructive operation | `DROP\s+(TABLE|DATABASE|SCHEMA)` | Destructive DDL statements |
| SQL table truncation | `TRUNCATE\s+TABLE` | Mass data deletion |
| Code eval injection | `eval\s*\(` | Dynamic code execution |
| Exec injection | `exec\s*\(` | Process spawning from user-controlled input |
| Prompt injection: instruction override | `ignore\s+(previous\|prior\|all)\s+instructions?` | Classic jailbreak phrasing |
| Prompt injection: disregard system | `disregard\s+your\s+(previous\|prior\|system)` | System prompt override attempt |
| DAN jailbreak attempt | `you\s+are\s+now\s+DAN` | "Do Anything Now" jailbreak |
| AWS access key detected | `AKIA[0-9A-Z]{16}` | AWS IAM access key ID |
| GitHub PAT detected | `ghp_[A-Za-z0-9]{36}` | GitHub personal access token |
| API secret key detected (OpenAI/Stripe) | `sk-[A-Za-z0-9]{20,}` | OpenAI / Stripe secret key format |
| Supply-chain: custom PyPI index | `pip\s+install\s+.*--index-url` | Dependency confusion / typosquatting |
| Supply-chain: custom npm registry | `npm\s+install.*--registry` | Custom npm registry override |
| Clone-and-execute | `git\s+clone\s+.*&&\s*(ba)?sh` | Cloning and immediately executing |
| SSH directory access | `~\/\.ssh\/` | Access to SSH key directory |
| Bash TCP reverse shell | `\/dev\/tcp\/` | Bash built-in reverse shell technique |

### MEDIUM severity

| Rule label | Pattern | What it catches |
|------------|---------|-----------------|
| Environment variable access | `process\.env` | Node.js env access (may expose secrets) |
| Dotenv file access | `\.env\b` | Reading `.env` files |
| Passwd file read | `cat\s+\/etc\/passwd` | Reading the Unix password database |
| SSH key manipulation | `ssh-add` | Adding SSH keys to the agent |
| Sensitive system file access | `\/etc\/(shadow\|hosts\|sudoers\|resolv\.conf)` | Unix security files |
| Base64 decode (JS) | `atob\s*\(` | Client-side base64 decode |
| Base64 decode (CLI) | `base64\s+-d` | Shell base64 decode |
| macOS Keychain access | `security\s+find-generic-password` | macOS keychain credential extraction |
| Python one-liner execution | `python[23]?\s+-c\s+["']import` | One-shot Python code execution |

### LOW severity

| Rule label | Pattern | What it catches |
|------------|---------|-----------------|
| Full table scan query | `SELECT\s+\*\s+FROM` | Potentially expensive/sensitive DB queries |
| World-accessible permission | `chmod\s+[0-7]*7[0-7]*` | Setting world-accessible bits |
| Sudo usage | `sudo\s+` | Privilege escalation |
| Global npm package install | `npm\s+install\s+--global` | System-wide package installation |
| Python package install | `pip\s+install\s+\S` | Python package installation |

## Adding custom rules

### Via the dashboard

1. Open ClaudeSec at [http://localhost:3000](http://localhost:3000).
2. Select **Protect → Rules** in the left navigation rail.
3. Click **Add Rule**.
4. Fill in:
   - **Pattern** — a JavaScript-compatible regular expression (e.g., `secretToken[=:]\s*\w+`)
   - **Severity** — `low`, `medium`, or `high`
   - **Label** — a short description shown in alert notifications (e.g., `Custom secret token pattern`)
5. Click **Save**.

The rule takes effect immediately — all future spans are evaluated against it. Existing spans are not retroactively re-evaluated.

<Note>
  Custom regex rules **detect by default** and follow the same convention as the built-ins: in `enforce` mode a **high- or critical-severity** custom rule also **blocks** the tool call before it runs (low/medium custom rules stay detect-only, and nothing custom blocks in `monitor` mode). The server mirrors your custom rules into the hook's `rules-enforcement.json` snapshot so the hook enforces the same set. To always-block a specific file or directory in *either* mode, add a **protected path** instead — see [Enforcement → Protected paths](/security/enforcement#protected-paths-always-on).
</Note>

### Via the API

```bash
curl -X POST http://localhost:3000/api/rules \
  -H 'Content-Type: application/json' \
  -d '{
    "pattern": "secretToken[=:]\\s*\\w+",
    "severity": "high",
    "label": "Custom secret token pattern"
  }'
```

All custom rules are evaluated with the `i` (case-insensitive) flag automatically applied. The API accepts `low`, `medium`, `high`, or `critical` for `severity`; the dashboard form offers the first three. A custom `critical` rule added via the API is not special-cased — in `enforce` mode it blocks exactly like a built-in high/critical rule.

## Regex pattern syntax

ClaudeSec uses JavaScript `RegExp` syntax. Key tips:

- Escape backslashes in JSON: `\s` becomes `\\s` in the JSON body.
- Patterns are case-insensitive by default (`i` flag is always added to custom rules).
- Use anchors (`^`, `$`) sparingly — patterns match anywhere in the concatenated attribute string.
- Test patterns at [regex101.com](https://regex101.com) using the JavaScript flavor.

### Example patterns

| Goal | Pattern |
|------|---------|
| Match any Stripe secret key | `sk_live_[A-Za-z0-9]{24,}` |
| Match `password=` in any context | `password\s*=\s*\S+` |
| Match base64-encoded strings (long) | `[A-Za-z0-9+/]{40,}={0,2}` |
| Match `curl` to an IP address | `curl\s+http://\d+\.\d+\.\d+\.\d+` |
| Match any `docker run` with `--privileged` | `docker\s+run\s+.*--privileged` |

## Deleting custom rules

### Via the dashboard

Click the trash icon next to any custom rule in the Rules tab.

### Via the API

```bash
curl -X DELETE http://localhost:3000/api/rules/custom-1700000000000-abc12
```

Built-in rules cannot be deleted, but they can be superseded by a custom rule that matches the same pattern with a different severity or label.

---

## Rule persistence

Custom rules are persisted in `rules.json` in the project root directory and survive server restarts. Built-in rules are compiled into `server/detection.ts` and are always present.
