ClaudeSec runs as a single local service: an Express backend that ingests agent activity, evaluates threat rules, and serves the dashboard. There are two ways to launch it. Pick the one that matches how you work.

| Path | Best for | Agent capture |
|---|---|---|
| **pnpm** (clone) | Local development and self-hosting | Local transcript watcher + OTLP |
| **Docker** | Servers, CI, and Windows | **OTLP only** (no host transcript watching) |

<Note type="warning">
  **Do not run `npx claudesec`.** ClaudeSec is not published to npm — the package is
  `private: true` — and the `claudesec` name on the public npm registry belongs to an
  unrelated project by a different author. Running `npx claudesec` would download and
  execute someone else's code, never something to do on the word of a security tool's
  own documentation. There is no npx path; install from source (below) or use Docker.
</Note>

Both serve the dashboard at **http://localhost:3000** and bind to loopback (`127.0.0.1`) by default. Your data lives in a local SQLite file — see [Where your data lives](#where-your-data-lives).

## Prerequisites

- **Node.js 22.13+** (Node 22 LTS recommended) — required for the pnpm path. The Docker path needs only Docker.
- **pnpm** via corepack (`corepack enable`) — required for the clone path.
- At least one supported agent: [Claude Code](/harnesses/claude-code), [GitHub Copilot CLI](/harnesses/copilot), or [Codex](/harnesses/codex).

<Note>
  `better-sqlite3` compiles a native module on install. If install fails, add the Xcode Command Line Tools (macOS) or `build-essential` (Linux) and retry. Docker sidesteps this entirely.
</Note>

## Option A — the background service (after cloning)

Once you have a clone (Option B), install the user-level background service —
launchd on macOS, a systemd user service on Linux — so ClaudeSec starts with your
machine and keeps tailing agent sessions in the background:

```bash
node cli/init.mjs
```

This starts the service and opens the dashboard at [http://localhost:3000](http://localhost:3000).
The local watcher begins tailing every agent session on your machine immediately.

Manage the service the same way:

```bash
node cli/init.mjs status   # health, span/session/alert counts, uptime
node cli/init.mjs stop     # stop and remove the service
node cli/init.mjs reset    # wipe stored data in ~/.claudesec/spans.db
```

## Option B — pnpm (clone, build, run)

For local development or self-hosting from source. The one-command starter installs, builds, serves the production app in the foreground, and reports which agents it can see:

```bash
git clone https://github.com/aanjaneyasinghdhoni/ClaudeSec.git
cd ClaudeSec
./start.sh
```

Prefer to run each step yourself:

```bash
corepack enable
pnpm install
pnpm build      # runs the test gate, then builds the dashboard into dist/
pnpm start      # serve the production build at http://localhost:3000
```

`pnpm start` runs the backend in production mode and serves the built dashboard. For active development with hot reload, use `pnpm dev` instead of `pnpm build && pnpm start`.

To keep ClaudeSec running across reboots, install the background service from your clone:

```bash
pnpm build
node cli/init.mjs            # install + start the service, open the dashboard
node cli/init.mjs stop       # stop and remove the service
```

See the [CLI reference](/reference/cli) for every command.

## Option C — Docker (OTLP only)

Docker is the right path for a server, a shared host, or Windows. The Compose file publishes the dashboard on loopback and persists the database in a named volume:

```bash
docker compose up
```

This builds the image, runs the backend on **http://localhost:3000** (published to `127.0.0.1` only), and stores data in the `claudesec-data` volume. The container sets `CLAUDESEC_TRUST_LOCAL=1`, which is safe **only** because the port is published on loopback — never expose the container port on a public interface without an auth token (see [Privacy & Security](/security/privacy)).

<Warning>
  **Docker ingests via OTLP only.** A container cannot read the transcript files on your host, so the zero-config local watcher does **not** run in Docker. Point your agents at the OTLP endpoint (below) to capture them. Everything else — detection, the dashboard, retention, enforcement config — works identically.
</Warning>

Want a synthetic dataset to explore without touching real telemetry? Bring up the demo container alongside it:

```bash
docker compose --profile demo up
```

The demo runs on its own port and a separate, physically isolated volume seeded with synthetic sessions. See the [Quickstart](/quickstart#try-it-with-synthetic-data-demo-container) for details.

## Platform notes

| Platform | Recommended path | Notes |
|---|---|---|
| **macOS** | pnpm | Background service via launchd is **verified**. Native local watcher. |
| **Linux** | pnpm | Background service via systemd user service (experimental). Native local watcher. |
| **Windows** | **Docker** | The local transcript watcher and the Scheduled Task service are experimental on Windows; the supported path is Docker with OTLP capture. |

The watcher and dashboard run anywhere Node 22.13+ runs; only the auto-start *service* layer is platform-specific. On any platform you can always run the foreground server.

## Connect an agent

ClaudeSec has two intakes, and both land in the same dashboard.

### Local agents — zero config (pnpm path)

If the agent runs on the **same machine** as ClaudeSec, you do nothing. The watcher tails the transcript directories your agents already write to:

- `~/.claude/projects` — Claude Code
- `~/.codex/sessions` — Codex
- `~/.copilot/session-state` — GitHub Copilot CLI

No environment variables, no shell-profile edits, no agent restart. Activity — including sessions that were already running — appears within seconds. See the [transcript watcher](/explanation/watcher) for how it reads and scrubs.

### Remote, CI, or Docker — OTLP

For agents on another host, in a container, or in CI — and for **any** ClaudeSec running under Docker — use the OpenTelemetry endpoint. ClaudeSec accepts standard OTLP/HTTP JSON at `POST /v1/traces`. Set two variables on the agent:

```bash
export OTEL_EXPORTER_OTLP_ENDPOINT=http://<claudesec-host>:3000/v1/traces
export OTEL_EXPORTER_OTLP_PROTOCOL=http/json
```

For Claude Code's native telemetry specifically (e.g. CI, where there's no transcript on the ClaudeSec host), also enable it agent-side:

```bash
export CLAUDE_CODE_ENABLE_TELEMETRY=1
export CLAUDE_CODE_ENHANCED_TELEMETRY_BETA=1   # model name + token counts
export OTEL_LOG_TOOL_DETAILS=1                  # tool names + input args
```

Full details, including reaching the server from another machine, are in [Capture remote & CI agents](/how-to/remote-agents).

## Where your data lives

Agent activity goes into one local SQLite database — by default `~/.claudesec/spans.db`, created with `0600` (owner-only) permissions. Override the path with `CLAUDESEC_DB`.

Everything else lives under `CLAUDESEC_HOME` (`~/.claudesec` by default): the Ed25519 audit signing key, the signed tail anchor, the control-plane pairing key, and the installed hook's config. **Back that directory up together with the database** — the hash chain cannot be verified without the signing key. See [What lives in `CLAUDESEC_HOME`](/reference/config#what-lives-in-claudesec-home-and-why-you-must-back-it-up).

Under Docker both live on the `claudesec-data` volume: the image sets `CLAUDESEC_DB=/data/spans.db` and `CLAUDESEC_HOME=/data/claudesec` as `ENV`, so a plain `docker run -v claudesec-data:/data` persists correctly without a Compose file.

<Warning>
  **If you built an image from a development commit, rescue your data before upgrading.** Images built from `master` or `feat/launch-hardening` between 2026-06-15 and the 2.0.0 release wrote the database *and* the audit signing key to `/home/node/.claudesec/` inside the container's writable layer, which is on no volume. Upgrading does not recover them, and removing the old container destroys both. Copy them out first:

```bash
docker cp claudesec:/home/node/.claudesec/spans.db ./spans.db
docker cp claudesec:/home/node/.claudesec/hooks ./claudesec-hooks
```

  Then put them on the volume at `/data/spans.db` and `/data/claudesec/hooks`. Upgrading from the released **1.3.0** image needs none of this — that data is already at `/data/spans.db`, where the new configuration points.
</Warning>

<Note>
  Replacing the named volume with a **host bind mount** on macOS or Windows can silently drop the `0600` mode on the database and the key files, because the file-sharing layer synthesises permissions. A named volume is stored on the Linux VM's own filesystem and keeps them.
</Note>

Upgrading a **clone** from 1.3.0 or earlier: the database used to be a bare `spans.db` resolved against your working directory, so it normally sat in the checkout. On first start it is moved once to `~/.claudesec/spans.db`, provided the new location is empty, `CLAUDESEC_DB` is unset, the file is a real SQLite database, and no other ClaudeSec process holds it. Otherwise it is left where it is and the server logs why. Set `CLAUDESEC_DB` to the old path if you would rather keep it there.

Nothing is sent anywhere by default. The dashboard binds to loopback, the database stays on your disk, and outbound sinks (webhooks, OTLP forwarding) are off unless you explicitly set them. See [Privacy & Security](/security/privacy) for the full data-handling model.
